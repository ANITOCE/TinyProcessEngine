## 1. 概述

### 1.1 背景与动机

TinyProcessEngine 目前由本地 CLI 枚举和打开进程，并在扫描交互中读写内存。远程连接让用户在机器 B 上使用同一套命令，检查和修改机器 A 上的目标进程。两端运行同一程序，通过启动参数选择 Server 或 Client。

### 1.2 可验证目标

- **G1 连接。** A 在默认端口或指定端口监听。B 输入 A 的 IP 和端口，Server 确认接纳后，两端均显示成功消息，B 进入 `TPE>`。
- **G2 会话。** Server 同时服务一个 Client。第二个 Client 得到明确的忙碌原因。当前连接结束后，下一次连接从干净的 `TPE>` 开始。
- **G3 远程操作。** B 能枚举、查找和打开 A 上的进程，并使用现有扫描命令读取和修改内存。对 A 上已知初值的测试进程完成扫描、读取、写入与回读。
- **G4 可观测性与回归。** Server 控制台记录连接和操作结果，Client 显示具体失败原因。Windows 和 Linux 的全量构建与测试通过，现有本地 CLI 契约继续通过回归验证。

### 1.3 非目标

并发客户端、账号与应用层鉴权、传输加密、自动重连和会话恢复、主机发现、GUI，以及公网部署。

### 1.4 范围

首版覆盖 Windows 和 Linux 的本地回环及受控 IPv4 网络。Server 按现有平台权限枚举、打开、读取和写入进程。Client 只操作当前连接的 Server。公网及不受信任网络属于范围外。

### 1.5 术语与前序指南

- **Server** 指持有目标进程和扫描状态的 TPE 实例。**Client** 指接收命令并展示结果的实例。
- **连接会话** 从 Server 接纳 Client 开始，到连接结束为止。**扫描会话** 从成功打开目标进程开始，到扫描层 `exit` 或连接结束为止。
- [First MVP 指南](first-mvp-guide.md)是已封存的前序基线。[CLI 交互规范](cli-interaction-spec.md)定义本地命令和扫描行为，其第 11.11 节同步本指南第 3 节的远程 CLI 契约。

### 1.6 备选方案、取舍与假设

- **转发命令行，已选定。** Client 发送用户输入的命令行，Server 复用本地命令解析和执行逻辑，回传结果及下一提示符。远程与本地的参数校验和错误行为由同一份逻辑决定。
- **Client 解析为按操作定义的请求。** 这种协议便于将来为其他入口提供结构化接口，首版需要为每种扫描操作维护请求和响应契约，并在 Server 校验数据。
- 需求方选定命令行转发，以现有 CLI 的行为一致性作为首版优先项。验收覆盖同一条命令在本地和远程的结果、提示符及失败处理。

## 2. Constitution（项目治理准则）

沿用 First MVP 已批准的项目治理准则和共同流程规范。P0 核对执行环境中的 Constitution 与已批准版本。在当前检出仍为模板时，按已批准条款恢复并核对。原则修订由需求方批准并记录。

- 测试先行，经人批准后观察预期 RED，再完成 GREEN 和适用的重构。Phase 收尾保留全量验证证据。
- 每个 Phase 使用现有检出中的独立特性分支，只有当前执行者写入。主干受保护，收尾方式由人决定。
- 维持现有 C++ 代码规范、错误传播与资源生命周期约定。Windows 和 Linux 全量构建零新增告警。第三方依赖通过 CMake 固定版本，并在 P3 验证平台兼容性和依赖许可。
- 无应用层鉴权的 Server 仅用于由网络访问控制限定的受控网络。任何可达监听端口且被接纳的 Client 都能请求 Server 权限允许的内存操作。

## 3. 全局技术约束与 CLI 契约

### 3.1 技术栈与职责

C++17、CMake 和 GoogleTest 延续项目现有约束。TCP 连接使用 [libhv](https://github.com/ithewei/libhv#tcp)，Server 控制台日志使用 [spdlog](https://github.com/gabime/spdlog#features)。P3 选定依赖版本、帧编码和大小上限，并核对项目的 CMake 最低版本。

Server 复用本地命令解析和执行逻辑。命令执行返回结果和下一交互状态，供本地终端或远程 Client 显示。Server 持有目标进程、扫描状态与下一提示符。Client 每次发送一条命令，收到响应后再发送下一条。TCP 消息有明确边界，结果可包含多行。Server 用明确的应用层响应接纳或拒绝会话，即使正在扫描也能回复忙碌。启动握手期限、帧格式与版本字段由 P3 定义。

### 3.2 启动与连接

```text
TinyProcessEngine.exe --server [-port <PORT>]
TinyProcessEngine.exe --connect <IP> -port <PORT>
```

- 两个启动模式互斥，Linux 使用对应的可执行文件名。Server 省略 `-port` 时使用 `8008`。Client 必须给出 Server 的 IPv4 地址和端口。端口为 `1` 至 `65535` 的十进制整数。
- Server 成功监听后显示 `Waiting for connection ...` 并等待 Client。接纳 Client 后显示 `Connection successful.`，随后在同一控制台显示来自该 Client 的操作日志。默认监听全部 IPv4 接口，以支持两台机器直接连接。部署侧限定端口可达范围。
- Client 收到接纳响应后显示 `Connection successful.` 和 `TPE>`。Server 忙碌时拒绝新会话，第二个 Client 显示 `Connection failed.` 和原因 `Server is busy.`，当前会话继续。
- 启动参数错误显示用法和具体原因，退出码为 `2`。绑定、握手或连接失败显示具体原因，退出码为 `1`。Client 建立会话前的连接失败同时显示 `Connection failed.`。

### 3.3 交互与会话结束

- `TPE>` 接受 `--all-processes`、`--search-process <PID>` 和 `--open-process <PID>`。前两条显示 Server 的结果并回到 `TPE>`。成功打开目标后显示 `<process-name>-equal-i32>`。打开失败显示原因并回到 `TPE>`。
- `TPE>` 的 `help` 或 `--help` 显示当前层的命令。扫描层沿用现有的 `help`、`new-scan`、`next-scan`、`list`、`write`、`undo` 及扫描提示符规则。普通命令失败后保留当前交互层，报告原因并等待下一条命令。
- 扫描层的 `exit` 释放目标进程和扫描状态，回到 `TPE>`，保留连接。`TPE>` 的 `exit` 或任一层的输入 EOF 正常结束 Client，退出码为 `0`。Server 继续监听。
- Client 检测到意外断线后显示原因并以 `1` 退出。等待命令响应时直接报告，等待终端输入时最迟在下一次输入后报告。若断线时正在等待写入响应，提示写入结果未知。再次连接由用户发起。空闲会话的断线检测依赖传输层的通知。
- Server 检测到断线后丢弃尚未开始的命令。已经开始的命令可以自然结束，随后释放当前会话并接纳下一位 Client。清理完成前仍返回忙碌。
- Server 在控制台记录连接、拒绝、断开及操作结果。操作日志包含时间、对端、命令名、可用的目标 PID 和结果摘要。日志字段限于这些元数据，扫描数据与写入值由命令响应交付。

### 3.4 双机交互示例

A 的 IPv4 地址为 `192.168.1.20`，其上运行 PID 为 `4321` 的测试进程。

```text
# A
TinyProcessEngine.exe --server
Waiting for connection ...
Connection successful.

# B
TinyProcessEngine.exe --connect 192.168.1.20 -port 8008
Connection successful.
TPE> --search-process 4321
Test.exe
TPE> --open-process 4321
Test.exe-equal-i32> new-scan 100
Test.exe-equal-i32-100> exit
TPE> exit
```

A 上的 `Connection successful.` 在接纳 B 时显示，之后 A 的控制台继续输出 B 的操作日志。

## 4. 开发路线图

### 4.1 路线图总览

### 4.2 Phase 条目

#### Phase 01 · 远程连接与进程查询

- 目标及范围 — G1、G2、G4。完成启动参数、应用层接纳、`TPE>`、进程枚举与查询、连接层退出及日志。`TPE>` 的帮助只列已交付命令，其他命令走未知命令处理。打开进程、扫描与内存操作归入 Phase 02。
- 依赖 — First MVP 已交付基线。
- 公开交付物 — 两种远程启动模式、远程进程查询和单连接接纳。
- 验收 — 默认端口和自定义端口均可接入。Server 先显示等待提示，接纳首个 Client 时两端均显示成功提示。首个 Client 可查 Server 进程，第二个 Client 得到忙碌原因和退出码 `1`。当前 Client 退出或断开后可重新接入。缺参、无效端口、端口占用和连接失败有明确输出及退出码。验证连接和查询日志，以及双平台本地回归。
- 状态 — `done`。2026-11-12 本地合入 `feat/add-remote-connection`，合入提交 `d7af096`。合入后 Windows 416 项、Linux 423 项全量测试通过，两端均为 0 失败。

#### Phase 02 · 远程扫描与内存读写

- 目标及范围 — G3、G4。完成远程打开进程、扫描命令、内存读写、扫描层退出和会话清理。
- 依赖 — Phase 01 已合入并通过合入后验证。
- 公开交付物 — 完整远程扫描 CLI、两层退出和远程内存操作验证。
- 验收 — B 打开 A 上的受控测试进程，用现有命令扫描已知值并通过 `list` 实时读取，再 `write` 并回读新值。覆盖续扫、撤销、进程打开失败、扫描层 `exit` 后打开另一个进程，以及扫描期间拒绝第二个 Client。覆盖断线期间的命令处理与清理后重连，并验证旧结果不会进入新会话。Windows 和 Linux 分别验证 Server 与 Client。跨平台连接至少完成一次真实写入和回读。
- 状态 — `done`。2026-11-14 本地合入 `feat/add-remote-connection`，合入提交 `52d3123`。合入后 Windows 419 项、Linux 426 项全量测试通过，两端均为 0 失败。已验证 Windows Client 向 Linux 上的受控进程写入并回读。

### 4.3 顺序

Phase 01 先固定连接和查询契约，独立验证后合入。Phase 02 在该基线上接入扫描和写入。每个 Phase 完整执行 P0–P13。
